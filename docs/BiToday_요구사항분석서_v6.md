## 0. 개요

### 0-1. 프로젝트 성격

- 실제 코인을 사고파는 **현물(Spot)** 이 아니라, 방향과 레버리지에 베팅하는 **선물(Futures)** 모의투자 플랫폼이다.
- 실제 돈이 아닌 **가상 포인트**로만 거래하며, 상업적 목적이 없는 팀 포트폴리오/취미 프로젝트다.
- 시세는 업비트에서 받아온 **현물 시세**를 기준가(마크 가격)로 사용하고, 롱/숏·레버리지·증거금·청산 로직은 **전부 자체 시스템이 시뮬레이션**한다.

### 0-2. 학습 목표 (프로젝트의 진짜 목적)

> 🎯 **이 프로젝트의 핵심 목표는 "수많은 거래를 어떻게 안정적으로 처리하는가"이다.**
기능 완성 자체가 목적이 아니라, **대용량 트래픽 상황에서의 동시성 제어 · 데이터 정합성 · 성능 최적화 · 시스템 안정성** 경험이 최우선 목표다.
> 
- 짧은 시간(0.n초)에 다수의 포지션 진입/종료/청산 요청이 몰릴 때, 서버와 DB가 정합성을 유지하며 안정적으로 버티는지를 실험·측정·개선하는 것이 핵심이다.
- 선물 도메인의 **청산(Liquidation)** 특성상, 동시성 문제가 도메인에 내장되어 있어 별도 인위적 설계 없이도 부하 테스트로 재현 가능하다.

### 0-3. 부하의 원천 (중요 — 무엇이 우리 시스템의 부하인가)

> ⚠️ "거래량 폭증 = 우리 시스템 부하"가 **아니다.** 부하의 원천을 정확히 구분하는 것이 이 프로젝트 설계의 출발점이다.
> 

| 구분 | 성격 | 우리 부하 여부 |
| --- | --- | --- |
| 업비트 시세 수신 (WebSocket) | 외부에서 흘러들어오는 **읽기 전용 스트림** | ❌ 아님 (업비트가 감당) |
| 유저의 포지션 진입/종료 요청 | 우리 서버의 **가용 포인트 검증·차감, 포지션 생성 등 DB 쓰기** | ✅ **이것이 우리 부하** |
| 청산 엔진의 포지션 모니터링·청산 처리 | 열린 포지션에 대한 주기적 조회 + 청산 시 DB 쓰기 | ✅ **이것이 우리 부하** |
- 즉, 최적화·안정성 실험의 대상은 **업비트 시세와 무관하게, 우리 DB에 대한 쓰기 경합**에서 발생한다.
- 이 부하는 전부 시스템 내부적이므로, **실제 유저 없이 부하 테스트 도구로 100% 재현 가능**하다. (6장 NFR 참고)

| --- | --- |

| **체결 방식** | **마크 가격 기반 즉시 체결(시장가)** — 유저 간 매칭(오더북) 미채택. 진입/종료 요청 시 대기 없이 즉시 체결한다. **체결가는 항상 서버가 보유한 최신 마크 가격이며, 클라이언트가 전송한 가격은 체결가로 사용하지 않는다.** 
(근거: 0-4 참고) |

| 포지션 모드 | **헤지(Hedge)** — 동일 코인에 롱/숏 및 복수 포지션을 독립적으로 동시 보유 가능. 모든 진입/종료/청산은 개별 포지션 단위로 처리 |
| 레버리지 | **1배 / 5배 / 25배 / 125배** 중 선택 |
| 펀딩비(Funding Rate) | **없음** (MVP 범위에서 제외, 추후 확장 가능) |
| 거래 수수료 | **없음** (MVP 범위에서 제외). 수수료를 도입하면 청산가 공식이 근사가 아니게 되고, 정합성 검증식 `최초 margin == SUM(margin_released)`가 어긋나 **동시성 버그와 수수료 차감을 구분할 수 없게 된다.** 상세 근거는 트레이드오프 문서 한계 8번 참고 |
| 시즌제 | 모의투자 플랫폼을 **시즌 단위로 운영.** 잔고·포지션·출석·순위가 모두 시즌에 귀속되며, 시즌 종료 시 잔고가 리셋된다 (7장 참고) |
| **최소 진입 증거금** | 진입 시 **증거금 기준** 최소 금액을 둔다. 명목가치 기준이면 125배에서 실제 지출이 무의미하게 작아진다(명목 5,000원 → 증거금 40원). 구체적 금액은 시즌 시드 확정 후 결정 |
| 청산 모델 | **바이낸스 모델 기반**, 단 유지증거금률(MMR)을 **0.5% 단일 고정값**으로 단순화 (tier 브라켓 미적용) |
| 청산 시 잔여 증거금 | 청산가 도달 시 **유지증거금(명목가치 × 0.5%)만큼 가용 포인트로 반환** |
| 마크 가격(Mark Price) | **업비트 현물 시세를 그대로 마크 가격으로 사용** (다중 거래소 종합 생략) |
| 데이터 정밀도 | 포인트·수량·가격은 PostgreSQL `NUMERIC`으로 정밀도 보장 (부동소수점 오차 금지) |

### 1-1. 계산식 참고

> ⚠️ 아래 청산가 공식은 **수수료·유지금액(maintenance amount)을 무시한 근사 공식**이다.
실제 적용 전 몇 가지 값으로 직접 계산해 검증할 것.
> 
- 명목가치(Notional) = 진입가 × 수량
- 필요 증거금 = 명목가치 ÷ 레버리지
- 미실현 손익(PnL)
    - 롱(Long): (마크 가격 − 진입가) × 수량
    - 숏(Short): (진입가 − 마크 가격) × 수량
- 청산가(격리, MMR 0.5% 단일 고정 기준, 근사)
    - 롱: 진입가 × (1 − 1/레버리지 + 0.005)
    - 숏: 진입가 × (1 + 1/레버리지 − 0.005)
    - 예) 진입가 20,000 / 10배 / MMR 0.5% → 롱 청산가 ≈ 18,100
- 수익률(ROE) = 미실현 손익 ÷ 증거금 × 100 (%)
- 참고: 레버리지 1배는 1/레버리지 = 1이므로 청산가가 진입가 × 0.005 수준으로 내려가,
마크 가격이 0에 근접하지 않는 한 사실상 청산되지 않는다(현물성 포지션).
- **부분 종료 시 청산가**: 청산가 공식에 수량이 포함되지 않고, O-11이 증거금을 비례 반환하므로 실효 레버리지가 유지된다. 따라서 **부분 종료 후에도 청산가는 변하지 않는다.** 예) 진입가 20,000 / 10배 / MMR 0.5% → 수량 10에서 3을 종료해도 청산가는 18,100으로 동일

## 0-4. 체결 방식 결정 근거 (즉시 체결 채택)

> 실거래소(바이낸스 선물)는 **오더북 + 매칭 엔진** 구조로, 유저들의 주문이 가격·시간 우선순위로 매칭되어 체결된다. bitoday는 이를 채택하지 **않고**, 마크 가격 기반 **즉시 체결(시장가)** 방식을 채택한다.
> 

**즉시 체결 방식 채택 근거:**

1. **유동성 문제 회피**: 매칭 방식은 거래 양측(사려는 사람/팔려는 사람)이 모두 있어야 체결된다. 모의투자는 유저 풀이 작아 오더북이 비어 있으므로, 매칭 방식이면 체결 자체가 성립하지 않는다. 즉시 체결은 상대방 유저가 필요 없어 이 문제를 원천 회피한다.
2. **스코프 관리**: 매칭 엔진(오더북 자료구조 + 우선순위 매칭 + 부분 체결 + 주문 취소)은 그 자체로 별도 프로젝트 규모다. 레버리지·청산과 결합 시 난이도가 과도하게 상승한다.
3. **학습 목표 정렬**: 이 프로젝트의 목적은 "매칭 엔진 성능"이 아니라 "잔고 정합성·청산 동시성"이다. 즉시 체결은 배우고자 하는 동시성 문제(DB 쓰기 경합)에 집중하게 해준다.

> 📌 마크 가격 = 업비트 단일 시세 사용(다중 거래소 종합 생략)과 동일한 성격의 **의도적 단순화**다. 실거래소 구조를 이해한 상태에서 모의투자 목적에 맞게 단순화한다는 일관된 설계 철학을 따른다.

| CH-04 | 시간봉 변경 | 사용자가 시간봉을 변경하면 해당 시간봉의 차트 데이터를 다시 조회하여 화면에 표시한다. |
| CH-05 | 차트 데이터 유지 | 차트는 최근 N개의 캔들 데이터를 유지하며, 새로운 캔들이 생성되면 가장 오래된 데이터를 제거하여 최신 데이터를 유지한다. |

## 4. Order (포지션 / 거래)

> 현물의 "매수·매도"가 아니라 **포지션 진입·종료** 개념이다. 유저 간 매칭이 아니라 **마크 가격 기반 즉시 체결(시장가)**로, 진입/종료 요청 시 대기 없이 그 시점 마크 가격으로 즉시 체결된다.
포지션 모드는 **헤지(Hedge)** 로, 각 포지션은 독립된 단위로 관리되며 동일 코인에 롱·숏 또는 복수 포지션을 동시에 보유할 수 있다. 모든 진입/종료/청산은 개별 포지션 단위로 처리된다.
> 

| 요구사항 ID | 기능명 | 상세 내용 |
| --- | --- | --- |
| O-01 | 롱 포지션 진입 | 상승에 베팅하여 롱 포지션을 연다. **서버 수신 시점의 최신 마크 가격으로 즉시 체결**하며, 해당 가격을 진입가로 기록한다. 클라이언트가 전송한 가격은 체결가로 사용하지 않는다. |
| O-02 | 숏 포지션 진입 | 하락에 베팅하여 숏 포지션을 연다. (체결가 산정 방식은 O-01과 동일) |
| O-03 | 레버리지 설정 | 포지션 진입 시 배율(1/5/25/125배)을 설정한다. |
| O-04 | 증거금 차감(격리) | 진입 시 (명목가치 ÷ 레버리지)만큼 포인트를 증거금으로 격리한다. **진입 전 가용 포인트 ≥ 필요 증거금 검증 필수.** |
| O-05 | 청산가 계산 | 진입 시 청산가를 산출하여 포지션에 기록한다. |
| O-06 | 미실현 손익 계산 | 열린 포지션의 실시간 손익을 마크 가격 기준으로 계산한다. |
| O-07 | 포지션 종료(전량, 수동) | 사용자가 직접 포지션 전량을 종료한다. 실현 손익을 정산하고 남은 증거금을 가용 포인트로 반환한다. **본인 소유·열린 상태 검증 필수.** |
| O-08 | 강제 청산(자동) | 마크 가격이 청산가에 도달하면 시스템이 자동으로 포지션을 정리한다. 격리이므로 손실은 해당 증거금 내로 한정되며, **청산 시 유지증거금(명목가치 × 0.5%)에 해당하는 금액을 가용 포인트로 반환한다.** |
| O-09 | 거래·포지션 내역 조회 | 포지션 진입/종료/청산 기록을 조회한다. |
| O-10 | 거래 시간 저장 | 진입·종료·청산 발생 시간을 저장한다. |
| O-11 | 포지션 부분 종료(수동) | 사용자가 포지션 수량의 일부만 종료한다. 종료 수량 비율만큼 실현 손익을 정산하고 해당 비율의 증거금을 가용 포인트로 반환하며, 진입가는 유지한 채 나머지 수량으로 포지션을 이어간다. **본인 소유·열린 상태·종료 수량 ≤ 보유 수량 검증 필수.** |
| O-12 | 슬리피지 가드(선택사항) | 진입·종료 요청에 `expectedPrice`(유저 화면에 표시된 가격)와 `maxSlippageBps`(허용 괴리)를 **선택 필드**로 받는다. 두 필드가 있으면 서버 마크 가격과의 괴리를 검증하여 허용치를 초과할 경우 체결하지 않고 거부한다. **필드가 없으면 검증 없이 최신 마크 가격으로 체결한다.** 부하 테스트 스크립트는 필드를 생략하여 순수 쓰기 경합만 측정한다. |
| O-13 | 포지션 추가 진입(물타기) | 이미 열린 포지션에 수량을 추가한다. 기존 진입(O-01/O-02)은 항상 새 포지션을 생성하므로, 추가 진입은 **대상 포지션을 명시적으로 지정하는 별도 동작**이다(헤지 모드이므로 자동 합치기는 취지에 어긋난다). 진입가를 가중평균으로 갱신하고 수량·증거금을 증가시킨 뒤 청산가를 재계산한다. **본인 소유·열린 상태 검증 필수.** 구현 순서는 O-11(부분 종료) 이후로 한다 |

## 5. Portfolio (포트폴리오 / 수익률)

| 요구사항 ID | 기능명 | 상세 내용 |
| --- | --- | --- |
| P-01 | 가용 포인트 조회 | 현재 거래에 사용 가능한(증거금으로 묶이지 않은) 포인트를 표시한다. |
| P-02 | 보유 포지션 조회 | 열린 포지션 목록과 방향/진입가/레버리지/증거금/미실현 손익을 조회한다. (헤지 모드이므로 동일 코인의 복수 포지션을 각각 표시) |
| P-03 | 수익률 계산 | 포지션별 ROE(미실현 손익 ÷ 증거금)를 계산한다. |
| P-04 | 총 자산 계산 | **가용 포인트 + 열린 포지션에 묶인 증거금 + 미실현 손익 합계**로 총 자산을 산출한다. |
| P-05 | 자산 비율 표시 | 포지션별 투자 비중을 제공한다. |
| P-06 | 순위 계산 | **시즌 종료 시점**의 **순수 거래 수익금**을 기준으로 순위를 결정한다. 순수 거래 수익금 = 최종 자산 − 지급받은 총 포인트(시즌 시드 + 출석/이벤트 지급). **출석 등으로 지급된 포인트는 순위에 영향을 주지 않는다(리더보드는 수익금으로만 판단).** 확정된 순위와 수익금은 시즌 결과로 저장되며(S-03), 이후 기준 변경에 소급 영향을 받지 않는다. |

## 6. 비기능 요구사항 (NFR) — 프로젝트 핵심 목표

> 이 섹션이 프로젝트의 **진짜 본체**다. 0-2 학습 목표("수많은 거래 처리")를 구체적 요구사항으로 명문화한다.
> 

| 요구사항 ID | 항목 | 상세 내용 |
| --- | --- | --- |
| NFR-01 | 동시성 제어 | 동일 계정에서 동시 포지션 진입 시 가용 포인트 차감의 정합성을 보장한다(race condition 방지). **비관적 락 / 낙관적 락 / 분산 락(Redis) 전략을 비교 실험**하고, 부하 테스트 지표(처리량·실패율·재시도 횟수)로 선택을 정당화한다. |
| NFR-02 | 트랜잭션 원자성 | 포지션 진입(증거금 차감 + 포지션 생성)과 종료(손익 정산 + 증거금 반환 + 상태 변경)는 각각 단일 트랜잭션으로 원자적으로 처리한다. |
| NFR-03 | 청산-수동종료 경합 제어 | 동일 포지션에 대해 자동 청산 엔진과 사용자 수동 종료(전량/부분)가 동시에 발생해도 **정확히 한 번만** 처리되도록 보장한다. (락 획득 후 상태 재확인 → OPEN일 때만 처리, 멱등성 보장) |
| NFR-04 | 데이터 정밀도 | 포인트·수량·가격은 `NUMERIC`으로 관리하여 부동소수점 오차를 방지한다. 코인 수량은 소수 단위(예: 0.001)를 허용한다. |
| NFR-05 | 실시간성 | 마크 가격 갱신 → 미실현 손익/청산 판정 반영까지의 지연을 최소화한다. 단, 마크 가격이 신선하지 않은 경우(C-07)에는 지연 최소화보다 **정합성을 우선하여 판정을 중단한다.** |
| NFR-06 | 부하 테스트 | 동시 거래·청산 시나리오를 부하 테스트 도구(k6 / Gatling / JMeter / nGrinder 등)로 재현·측정한다. **가상 유저 = 실제 사람이 아닌 HTTP 요청 스크립트**이므로, 별도 테스트 코인 없이 기존 코인으로 우리 API에 트래픽을 발생시켜 재현한다. (세부 시나리오는 6-1 참고) |
| NFR-07 | 청산 엔진 처리량 | 다수의 열린 포지션에 대한 청산가 모니터링을 주기적으로 안정적으로 수행한다. 대량 동시 청산 상황에서도 처리량을 유지한다. |

### 6-1. 부하 테스트 시나리오 (NFR-06 세부)

| 시나리오 | 재현 방법 | 측정·관찰 대상 |
| --- | --- | --- |
| **동시 진입 폭주** | 가상 유저 N명이 같은 순간 롱/숏 진입 요청 | API 처리량(TPS), 응답 시간이 무너지는 임계점 |
| **핫 계정(Hot Row) 경합** | 소수 계정에 요청을 집중시켜 동일 행(row)에 락이 몰리게 함 | 락 전략별(비관적/낙관적) 처리량·재시도·실패율 차이 → NFR-01 정당화 근거 |
| **청산 엔진 부하** | 열린 포지션을 대량 사전 생성 후, 마크 가격 급변으로 대량 동시 청산 유발 | 청산 엔진 처리량, 청산-수동종료 경합 정확성 → NFR-07 검증 |

> 📌 **측정 방법론 주의**: 부하 테스트는 배포 후 프로덕션이 아니라 **로컬/스테이징에서 먼저** 수행한다. 단일 인스턴스에 곧바로 과부하를 주면 "DB 경합 병목"인지 "인스턴스 스펙 한계"인지 구분되지 않으므로, 병목을 단계별로 분리하여 측정한다.

## 7. **Season (시즌 / 티어)**

> 모의투자는 **시즌 단위**로 운영된다. 잔고·포지션·출석·순위가 모두 시즌에 귀속되며, 시즌이 바뀌면 잔고가 리셋된다. 도입 이유: ① 125배 레버리지 특성상 파산이 잦은데 리셋이 없으면 유저가 이탈한다 ② 영구 누적 리더보드는 먼저 시작한 사람이 압도적으로 유리해 신규 진입 동기가 사라진다 ③ 포인트 숫자가 무한히 커지는 것을 통제한다.
> 

| **요구사항 ID** | **기능명** | **상세 내용** |
| --- | --- | --- |
| S-01 | 시즌 관리 | 시즌은 이름·시드 포인트·시작 시각·종료 시각·상태(예정/진행중/종료)를 가진다. **동시에 진행 중인 시즌은 하나만 존재한다.** |
| S-02 | 시즌 참가 및 시드 지급 | 진행 중인 시즌에 처음 참가하는 회원에게 해당 시즌의 시드 포인트를 지급한다. 잔고는 **시즌별로 독립 관리**되며, 이전 시즌 잔고는 보존된다. |
| S-03 | 시즌 종료 정산 | 시즌 종료 시각에 ① **열린 포지션을 전량 강제 종료**하고(종료 시각 마크 가격 기준) ② 최종 자산·순수 거래 수익금·순위·티어를 산정하여 **시즌 결과로 확정 저장**한다. 확정된 결과는 이후 기준 변경에 영향받지 않는다. |
| S-04 | 시즌 결과 조회 | 회원별 과거 시즌 결과(순위·티어·순수 거래 수익금)를 시즌 목록 형태로 조회한다. |
| S-05 | 티어 산정 | 시즌 종료 시점의 **순수 거래 수익금**을 기준으로 티어(브론즈/실버/골드 등)를 부여한다. **잔고가 아닌 순수 거래 수익금 기준**이어야 한다 — 잔고 기준이면 출석만으로 티어가 오르므로 M 도메인에서 해결한 순위 공정성 문제가 되살아난다. 임계값은 정책으로 정한다. |

> 📌 **시즌 최고 티어(peak)는 제공하지 않는다.** 미실현 손익을 포함해 정의하면 마크 가격이 갱신될 때마다 전 회원의 자산을 재계산하고 기록해야 하므로, "업비트 시세 수신은 우리 부하가 아니다"(0-3)라는 전제가 무너진다. 실현 기준으로 정의하면 체결 이력에서 복원 가능하므로 별도 저장이 불필요하다.
>

## 8. 변경 이력

### v1 → v2

- **성격 전환**: 현물(Spot) → 선물(Futures) 모의투자로 프로젝트 성격 자체를 재정의.
- **용어 통일**: 화폐 단위를 "포인트"로 통일 (v1의 P-04 "현금" 잔재 수정).
- **Order 도메인 재작성**: 매수/매도 → 롱/숏 포지션 진입·종료, 레버리지, 증거금, 청산가, 미실현 손익 개념 추가.
- **Portfolio 재정의**: 총 자산 = 가용 포인트 + 증거금 + 미실현 손익.
- **Coin 도메인**: 마크 가격(C-06), Market(MK)·Chart(CH) 세부 요구사항 추가.
- **NFR 섹션 신설**: 동시성·정합성·부하 테스트 등 프로젝트 핵심 목표를 요구사항으로 명문화.
- **정책 확정**: 격리 증거금 / 펀딩비 없음 / 바이낸스 모델 기반(MMR 0.5% 단일 고정) / 마크 가격 = 업비트 현물 시세.

### v2 → v3 (미결정 사항 확정 반영, 26.07.05)

- **부분 종료 지원 확정** → O-11 신규 추가. O-07은 "전량 종료"로 명확화.

> 4. **시즌 시드 금액과 시즌 기간**: 최소 진입 증거금과 티어 임계값이 여기에 연동되므로 먼저 정해야 한다.

> 7. **마크 가격 보관 위치**: 애플리케이션 메모리 vs Redis. 인스턴스 수와 청산 엔진 다중화 여부에 따라 결정한다.
